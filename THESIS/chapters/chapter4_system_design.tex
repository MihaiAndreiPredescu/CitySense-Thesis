\chapter{Requirements Analysis and Specification}

This chapter starts the practical part of the thesis. Following the standard software engineering workflow described by Sommerville \cite{sommerville2010}, the first step is to define what the application should do, who will use it, and what constraints the implementation must respect. For this reason, the chapter contains the scope of the project, the stakeholders, the functional requirements, the non-functional requirements, and the main data and API specifications.

\section{Project Scope}

CitySense is intended to be a focused prototype for pothole reporting. The application is not a complete municipality platform with authentication, notifications, maintenance dispatching, or billing integration. The scope was intentionally reduced so that the implemented features remain coherent, testable, and demonstrable end to end.

The main scope boundaries are clear. The project focuses on potholes, not on a large taxonomy of public issues, and the citizen workflow is Android-first. The backend stores and manages reports, but it does not integrate with an external city hall system. The administrative interface supports visualization and status change, but not complex maintenance planning.

\section{Stakeholders}

Even if the prototype is small, it still has several stakeholders. The citizen user is the person who notices a pothole, takes a photo, and sends the report. The administrator checks the dashboard, sees the location of reports, and marks issues as resolved. The developer or maintainer is responsible for configuring the backend, training the detector, and updating the system. The municipality is the final institutional beneficiary of cleaner and more structured report data.

The most important design decision that follows from this stakeholder analysis is that the citizen interface must stay extremely simple, while the backend and dashboard are allowed to carry more complexity.

\section{Main Usage Scenario}

The basic usage scenario of CitySense is straightforward. A citizen sees a pothole and opens the mobile app. The app requests camera and location permissions if necessary, and the user takes a photo and confirms the submission. The app stores the photo, coordinates, capture time, and a client-side report identifier locally. If the backend is reachable, it receives the image and metadata immediately; otherwise, the report remains queued on the phone. The detector classifies the issue as a pothole or rejects the image, after which the database checks whether a nearby pothole was already reported. The system then either creates a new report or increments the upvote counter of an existing one, and the report becomes visible on the map and in the dashboard.

This scenario guided the design of the rest of the requirements.

\section{Requirements for the Two Main Application Flows}

The implementation is organized around two main application flows. The first is the report submission flow, where the user captures a photo, obtains location, sends the report, and receives feedback. The second is report visualization and management, where the system displays active reports on a map and allows an administrator to resolve them.

These two flows cover the most important citizen-facing and administrator-facing behavior, and they also map well to the most important requirements from the previous section.

\section{Use Cases}

\subsection{Use Case 1: Submit a Pothole Report}

The actor is the citizen user. The preconditions are that the mobile app is installed and opened, and that camera and location services are available.

In the main flow, the user taps the report button and the app requests location if needed. The user captures a pothole photo, then the app saves the image, coordinates, capture time, and client report identifier locally. If the backend is reachable, the app uploads the saved report and the backend processes the request. The user then receives a success or error message.

The postcondition is that a new report is created or merged with an existing one. In the alternative flow, if the backend cannot be reached, the local report remains in the offline queue. The application retries synchronization when connectivity changes or when the app is resumed. Once the backend is reachable on the configured network address, the queued report is sent using the same client report identifier.

\subsection{Use Case 2: View Active Reports}

The actor is the citizen user or administrator. In the main flow, the user opens the map screen and the app requests the list of open reports from the backend. The reports are rendered as map markers. When the user taps a marker, the application shows details such as confidence, status, upvotes, coordinates, and the date and time when the last photo report was taken. The postcondition is that the user understands where active pothole reports are located.

\subsection{Use Case 3: Resolve a Report}

The actor is the administrator. In the main flow, the administrator opens the dashboard and filters or selects a report. The status is changed from \texttt{OPEN} to \texttt{RESOLVED}, and the map and report list are refreshed. The postcondition is that the resolved issue no longer appears in the default open-report view.

Offline synchronization also introduces a small receipt table, \texttt{report\_\allowbreak client\_\allowbreak submissions}. It stores the client-generated report UUID, the backend report to which it was applied, and whether that submission was merged as a duplicate. This table prevents an offline retry from incrementing the same pothole twice if the first upload succeeded but the phone did not receive the response.
