\chapter{Application Design, Implementation and Testing}

This chapter continues the practical part of the thesis. After defining the requirements in the previous chapter, the next step was to decide how the system should be organized and then implement the main functionalities. In this chapter I present the architecture of the application, the main implementation choices, and the way in which the final result was tested.

\section{General Architecture}

CitySense is organized as a client-server application with a small administrative web layer. The user-facing side is represented by the Flutter mobile application and the local offline report queue on the phone. The server side contains the FastAPI backend, the PostgreSQL/PostGIS database, the YOLO-based detection service integrated in the backend, and the administrator dashboard rendered in the browser.

The flow between these components starts when the mobile app captures the image and the user location. The app stores the report locally together with the capture time and a client-generated UUID, then sends the report to the backend through the REST API when the configured backend address is reachable. If the backend is not reachable, the queued report is still visible on the mobile map and can be inspected from a local detail sheet. The backend stores the uploaded image, runs the detector, checks for a nearby duplicate through PostGIS, and either stores or merges the report in the database. The app and the dashboard then request the list of reports and render them on a map.

This architecture was chosen because it keeps heavy logic out of the phone and makes the backend the single source of truth, while still allowing a citizen to record a report in places where the local backend network is temporarily unavailable.

\section{Deployment with Docker Compose}

The backend side of CitySense is run through Docker Compose \cite{docker_compose_docs}. For this project, Docker Compose has the role of starting the services that must work together for the application to function. Instead of manually installing and configuring a database server, PostGIS extensions, Python dependencies, environment variables, and ports, the project describes the local backend environment in one configuration file.

The database service uses the public \texttt{postgis/postgis} image, while the backend service is built from the project's Dockerfile. The backend depends on the database health check, which means that it starts only after PostgreSQL is ready to accept connections. This matters because the backend initializes and queries the database during normal operation.

The port mapping \texttt{8000:8000} makes the FastAPI application available through port 8000 on localhost. This is the address used for the admin dashboard during local testing. The port mapping \texttt{5432:5432} exposes the database for local inspection and debugging. Compose also defines persistent storage for the database through a named volume and maps the local model and upload folders into the backend container. Because of that, uploaded images and trained detector weights remain available outside the container lifecycle.

Inside the Compose network, the backend connects to the database using the service name \texttt{db}, not \texttt{localhost}. This is why the database URL contains \texttt{@db:5432}. In simple terms, Docker Compose creates a private local network where the containers can find each other by service name.

For development and demonstration, the main commands are:

\begin{verbatim}
docker compose up --build
docker compose up -d
docker compose logs backend
docker compose down
\end{verbatim}

This deployment model is suitable for the project because it makes the backend reproducible. A reviewer or developer does not need to manually reconstruct the backend environment; the required services and their relationships are documented in the Compose file.

\section{Design of the Mobile Application}

The mobile application was designed around two screens, because this was enough to cover the main use cases and kept the interface easy to understand.

\subsection{Report Screen}

The report screen is the most important part of the citizen workflow. It contains a photo preview area, a short status card with user feedback, an offline queue status card when reports are waiting to be synchronized, and a button that triggers the camera flow and submission.

The implementation is intentionally direct. I wanted the user to understand immediately what the app is for. There are no advanced menus, no long forms, and no extra fields that could slow down the interaction. Internally, however, the report is first saved on the phone and then submitted from that saved copy. This makes the online and offline paths use the same data structure. A screenshot of this interface is shown again in Figure~\ref{fig:app_interface}.

\subsection{Map Screen}

The second screen shows reports on a map. It combines two sources of information: synchronized open reports returned by the backend and queued offline reports stored locally on the phone. Server reports are shown with orange markers whose size increases with the upvote count, while local queued reports are shown with blue upload markers. A tray at the bottom summarizes how many reports are synchronized and how many exist only on the phone.

If a server marker is tapped, the application shows a details sheet with the issue type, confidence, status, upvote count, coordinates, and the date and time when the last photo report was taken. If a queued marker is tapped, the sheet instead shows the saved photo, coordinates, capture time, queue time, retry count, and last sync message. This removes the earlier empty-map experience where the user had to leave the map screen to understand what had been saved offline.

The map layer uses OpenStreetMap tiles through \texttt{flutter\_map}. The current implementation wraps the tile loading in an \texttt{OfflineMapTileProvider}. Tiles that load successfully are stored in the application cache, so previously viewed areas can still be displayed without network access. Missing offline tiles are transparent, and a single generated fallback basemap is drawn underneath the tile layer. This avoids a visually broken map when the phone is offline while still allowing real cached map tiles to appear whenever they exist.

This screen covers the visualization functionality because it demonstrates that submitted reports are not just stored, but also visualized in a meaningful way.

\subsection{How the Application Works in Practice}

In normal use, the citizen opens the application on the report tab, captures a photo, and allows the app to read the current location. The app immediately copies the photo into its own storage and writes a local queue entry containing the image path, latitude, longitude, capture time, retry state, and client report UUID. This local write happens before the network request, so the report is not lost if the backend is unavailable.

After the local save, the synchronization service checks the backend health endpoint. If the backend can be reached on the configured local network address, the app uploads the queued report as a multipart request. If the backend cannot be reached, the report remains in the offline queue, appears on the map as a local saved report, and the interface informs the user that it will synchronize automatically. The same queue is retried when connectivity changes, when the app returns to the foreground, and every 30 seconds while pending reports exist. On the backend, the client report UUID makes the retry idempotent: a repeated upload for the same local report returns the already-associated backend report instead of increasing the upvote counter twice.

When a previously offline report is finally processed by the backend, the app stores a short verification event. The shell consumes this event and displays an alert dialog containing the original captured photo. If the backend accepts the image, the dialog says that a pothole was confirmed and whether it was added or merged. If the backend rejects the image, the dialog explains that no pothole was detected and that no report was added to the map or dashboard.

\subsection{Internal Flutter Structure}

Inside the mobile project, the code is split into configuration, models, services, screens, and widgets. This was an intentional choice. Even though the project is not extremely large, placing all logic in one screen file would have made the code difficult to maintain. The configuration layer keeps application constants such as the backend URL, while the models contain data objects such as reports and statuses. The services handle API communication and location access, the screens define the main pages of the app, and the widgets contain reusable interface pieces.

The offline support is implemented in the service layer. The \texttt{Offline\allowbreak Report\allowbreak Repository} stores pending reports in a local SQLite database and copies the image into the application documents directory so it is not lost when the camera cache is cleaned. It also exposes the queued reports to the map screen. The \texttt{Report\allowbreak Sync\allowbreak Service} listens for connectivity changes, checks the backend health endpoint, retries pending reports periodically, and uploads pending reports in chronological order. The same service is also triggered when the application returns to the foreground. This means that when the phone reconnects to the same network as the backend and the configured API address becomes reachable, queued reports are sent without requiring the user to repeat the capture flow.

The map tile cache is implemented separately from the report queue. The \texttt{Offline\allowbreak Map\allowbreak Tile\allowbreak Provider} stores successfully downloaded OpenStreetMap tiles in the application cache directory. During offline use, it returns cached tile bytes when they exist and transparent tiles when they do not. A custom painter behind the tile layer draws a coherent fallback basemap so that local report markers still have geographic context instead of appearing on a blank surface.

\section{Design of the Backend}

The backend was implemented as a modular FastAPI application. I kept the routing layer small and moved the business logic into dedicated services. This decision made the code clearer and also made the chapter easier to write because each service has a well-defined responsibility.

\subsection{Configuration Layer}

The configuration layer reads environment variables such as the database URL, detector mode, model path, duplicate radius, and allowed CORS origins.

This is important because it separates code from deployment details. For example, the application can run in a local demo mode without changing the source code.

\subsection{Persistence Layer}

The persistence layer is built with SQLAlchemy and PostgreSQL. The report entity matches the specification from the previous chapter. Besides the normal numeric and text fields, the model also includes a spatial \texttt{location} field. That field is the one used by PostGIS during the duplicate check. The backend also stores \texttt{captured\_\allowbreak at}, which represents when the photo was taken on the phone, and \texttt{last\_\allowbreak photo\_\allowbreak reported\_\allowbreak at}, which represents the newest photo time among merged duplicate submissions.

\subsection{Detection Service}

The detection service wraps the YOLO model. It can work in yolo mode, where it loads a real checkpoint from disk, or in demo mode, where it returns a deterministic pothole-like result for smoke testing.

The demo mode was useful because it allowed me to verify the API flow, database insertion, and mobile feedback even when a final trained model was not available. At the same time, the code still keeps the real detector path as the intended production-like behavior.

\subsection{YOLOv8 Dataset, Training, and Weight Integration}

The real detection mode uses a YOLOv8 checkpoint trained specifically for the \texttt{pothole} class. The starting point was the lightweight \texttt{yolov8n.pt} model from Ultralytics \cite{jocher2023ultralytics}. This model is small enough to run on the available CPU hardware, while still being expressive enough for a single-class pothole detector.

The dataset was exported in YOLOv8 format from Roboflow Universe \cite{roboflow_universe}. The final local dataset structure used by the project is:

\begin{verbatim}
DATASET/
  train/
    images/
    labels/
  valid/
    images/
    labels/
  test/
    images/
    labels/
  data.yaml
\end{verbatim}

The \texttt{data.yaml} file exposes a single class:

\begin{verbatim}
train: train/images
val: valid/images
test: test/images

nc: 1
names: ['pothole']
\end{verbatim}

Before training, the dataset was checked for missing labels, invalid class identifiers, and non-normalized YOLO bounding boxes. The empty label files were kept intentionally because they represent background images where no pothole is visible. Such images are useful because they teach the detector not to create a report for every road scene.

The dataset split is summarized in Table~\ref{tab:yolo_dataset_split}. The number of boxes is higher than the number of images because one image may contain several potholes.

Training was performed on the local CPU environment with Python 3.12.10, Ultralytics 8.4.42, and PyTorch 2.11.0 CPU. The GPU check did not detect CUDA on the machine, so the training command was configured for CPU execution and Windows-safe data loading:

\begin{verbatim}
yolo detect train ^
  model=yolov8n.pt ^
  data="C:\UBB\THESIS\DATASET\data.yaml" ^
  epochs=50 ^
  imgsz=416 ^
  batch=8 ^
  device=cpu ^
  workers=0 ^
  project="runs/pothole" ^
  name=yolov8n_cpu_50
\end{verbatim}

The final training run lasted approximately 13,713 seconds, or about 3.8 hours. The best model weight was copied into the backend model directory as:

\begin{verbatim}
CitySense_Project/backend/data/models/pothole_yolov8n.pt
\end{verbatim}

The backend reads this file through the \texttt{MODEL\_PATH} environment variable when \texttt{DETECTOR\_MODE=yolo}. A small metadata file, \texttt{pothole\_yolov8n.metadata.json}, stores the training settings, dataset counts, metrics, and calibrated runtime threshold so that the deployed checkpoint can be traced back to the experiment that produced it.

The mobile application does not run the model directly. It only sends the image and location to the backend. This keeps the phone application lighter and makes it possible to update or replace the model without reinstalling the mobile app.

\subsection{Detector Runtime Configuration}

The deployed detector configuration is part of the backend environment. For the trained checkpoint used in the implemented system, the relevant values are:

\begin{verbatim}
DETECTOR_MODE=yolo
MODEL_PATH=data/models/pothole_yolov8n.pt
MIN_DETECTION_CONFIDENCE=0.65
DETECTOR_IMAGE_SIZE=416
DETECTOR_IOU_THRESHOLD=0.50
\end{verbatim}

The \texttt{PotholeDetector} service loads the checkpoint lazily the first time an image is processed. It then runs inference with the configured confidence threshold, image size, and non-maximum suppression IoU threshold. The detector filters predictions by class name and accepts only labels that normalize to \texttt{pothole}. From the accepted detections, the backend stores the highest-confidence result as the confidence value of the report.

The same values are exposed through the health endpoint. This makes it possible to verify during a demonstration that the backend is actually using the YOLO detector, the expected model path, the calibrated threshold, and the same image size used during calibration.

\subsection{Report Service}

The report service contains the main business logic. It receives the coordinates, the detection result, the capture time, the optional client report identifier, and the image metadata. Then it decides whether a new report should be created or whether the request should be merged into an existing report. This is where the spatial duplicate logic is applied. The service also stores \texttt{last\_photo\_reported\_at}, which is initialized when a pothole is first reported and refreshed whenever a duplicate photo report is merged into the same open issue.

For offline synchronization, the service records every client report identifier in the \texttt{report\_client\_submissions} table. If the same identifier is received again, the backend returns the already-associated report instead of applying the mutation a second time. This makes retries safe when the mobile app loses connectivity after an upload but before receiving the HTTP response.

\section{Duplicate Merge Logic}

The duplicate merge logic is one of the most important design choices in the whole application. Without it, the map would quickly become cluttered with almost identical markers. The implemented rule is simple:

\begin{quote}
If the detector label is compatible with pothole and there is an open pothole report within 10 meters, then increment the upvote count of the existing report.
\end{quote}

Otherwise, create a new report.

This rule is easy to explain, easy to implement, and easy to test. It is also intuitive from the user perspective. If several people report the same pothole, the system should treat that as evidence of urgency, not as several independent defects.

\section{Administrator Dashboard}

The administrator dashboard was implemented as a lightweight web page served by the backend. It uses Leaflet and OpenStreetMap tiles and provides a report list, a map with report markers, report details such as confidence and upvotes, the date and time when the last photo report was taken, a filter by report status, and a button for marking reports as resolved. The map and list are connected in both directions: the report card can focus the map on its location, while clicking a marker opens the popup, scrolls the left-side list to the same report, and highlights that card. The page also refreshes periodically and when it becomes visible again, so reports synchronized from the phone appear on the dashboard without requiring a manual refresh.

The dashboard is shown in Figure~\ref{fig:admin_dashboard}. I kept the design simple on purpose. For this prototype, the important point was to show that the backend data can be consumed by an administrative interface and that the report lifecycle can be closed when an issue is solved.

\section{Building the Pothole Reporting Flow}

The full pothole reporting flow is the central feature of the application because it connects the mobile interface, offline queue, backend API, detector, and database.

In this flow, the app requests location access, opens the camera, captures and previews the image, and saves the image, coordinates, capture time, and client report identifier locally. It then sends the saved report when the backend is reachable, receives the response from the backend or keeps the report queued, and displays either success, merge, offline queue, or error feedback. If the report was captured offline, the map screen shows it immediately as a local report. After synchronization, the app shows a verification dialog with the captured image and the backend decision.

This flow was implemented and tested end to end. The result is visible not only on the report screen, but also later in the map and dashboard. The offline queue keeps the citizen action short even when the phone is not currently connected to the backend network.

\section{Report Visualization and Management}

Report visualization and management forms the second main application flow. In the mobile app this means showing synchronized open reports and local queued reports on the map. In the administrative side this means being able to inspect the report list and change the status of an issue to resolved. The map behavior is deliberately connected to the offline queue so the citizen can see that a saved capture has a location and is waiting for backend verification.

This functionality is important because it shows that the application is more than just an upload form. It also has a full read-and-manage cycle.

\section{Testing Approach}

The testing strategy of the project was mostly functional and scenario-based. Because the system depends on mobile permissions, file uploads, detector integration, containerized services, and a spatial database, the most useful tests were the ones that follow the actual user flow. I also added a small automated test for the demo detection service and a backend test run inside the Docker container.

The testing environment used Docker Compose for PostgreSQL, PostGIS, and backend execution. MiKTeX was used for compiling the written document, the Android emulator was used for the Flutter mobile application, and Chrome was used for web-oriented smoke tests.

\section{Detector Evaluation and Calibration}

The detector was evaluated in two ways. First, the Ultralytics validation command was used to compute standard object-detection metrics on the validation and test splits. Second, the confidence threshold was calibrated separately because the best threshold for a civic reporting application is not always the default value used for visual experimentation.

\begin{verbatim}
yolo detect val ^

  imgsz=416 ^
  device=cpu ^
  workers=0
\end{verbatim}

After the model was trained, a confidence sweep was performed at IoU 0.5. The purpose was to choose a threshold that fits the application, not only the benchmark. A low threshold detects more potholes, but it may create false civic reports. A high threshold creates fewer false positives, but it can miss real potholes. The calibration was first selected on the validation split and then checked on the test split.

The backend script used for this step is:

\begin{verbatim}
python scripts/calibrate_confidence_threshold.py ^
  --model data/models/pothole_yolov8n.pt ^
  --dataset-root C:\UBB\THESIS\DATASET ^
  --split valid ^
  --imgsz 416 ^
  --device cpu
\end{verbatim}

\section{Database Integration of Detector Results}

The trained model does not write to the database directly. Instead, the database is updated only after the backend has completed the full validation pipeline. The uploaded file is saved in the runtime upload directory, the YOLO detector runs with the calibrated threshold, and non-pothole labels or low-confidence detections are rejected. After that, the highest-confidence pothole detection is converted into a \texttt{DetectionResult}. The report service checks PostGIS for an open nearby pothole, and the database either inserts a new row or increments the upvote count of an existing row.

The database is therefore not used for model training. Its role is operational: it stores accepted detections, their confidence score, the image path, location, status, and upvote count. This separation is important. The training dataset is a labelled computer-vision dataset, while the application database is a live reporting database.

\section{Discussion}

From the practical implementation, several conclusions became clear.

First, the project works best when the scope is kept narrow. Supporting only potholes made the detector contract, the database schema, and the user interface much easier to manage. Second, the geospatial merge logic adds real value because it avoids clutter and gives the administrator a better priority signal. Third, the offline user experience is better when local data is treated as part of the visible application state, not only as a hidden retry buffer. Showing queued reports on the map and later explaining the backend decision makes the application feel more predictable. Fourth, even a simple dashboard is enough to make the stored reports operationally useful.

There are also limitations. The current prototype does not include authentication, push notifications, municipality-specific work orders, or a multi-class damage taxonomy. The trained detector is also limited to the visual domain of the available pothole dataset. However, the project now includes a real YOLOv8 checkpoint, a documented training run, quantitative validation and test metrics, and a calibrated threshold connected to the backend runtime configuration. This makes the application more than a UI prototype: it demonstrates the complete loop from image capture to model inference, database insertion or merging, map visualization, and administrative resolution.
